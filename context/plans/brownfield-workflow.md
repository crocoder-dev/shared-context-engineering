# Plan: brownfield-workflow

## Change summary

Add `/brownfield` as the sixth canonical SCE workflow across OpenCode, Claude, and Pi. The workflow reconstructs durable `context/` memory from an existing repository's own evidence — current code first, then tests/schemas/migrations/build and runtime configuration, then discovered documentation, then at least three months of Git history — scores every important fact for confidence, blocks on anything it cannot resolve, discloses material contradictions, infers the `context/{domain}/` structure, and writes the result.

Evidence is strictly local: an explicit documentation-discovery sweep across the repository plus any additional local paths passed as arguments. The workflow performs no network access and no external documentation lookup.

`/brownfield` never creates the `context/` root. When `context/` is absent it renders a bootstrap gate for `sce setup --bootstrap-context` and stops, matching every other workflow. It runs no synchronization phase and invokes no sibling skill: it fills `context/` with what it found and reports.

Writes are additive by default — missing files and missing domains only, never overwriting or deleting an existing context file. An explicit leading `rebuild` argument grants rewrite authority over existing context files.

This uses the established thin-command, self-contained-skill, catalog-driven cross-target Pkl architecture, exactly as `/handover` did. It adds no routing agent, no phase package, and no Rust CLI change.

## Constraints and non-goals

- **In scope:** Project-root `.pi/` behavioral baseline; `config/pkl/base/workflow-brownfield.pkl`; the typed workflow catalog and shared composite renderer wiring; OpenCode, Claude, and Pi command/prompt plus skill-package generation; exact inventory, artifact-count, and required-content checks; repository-root `.pi`/`.claude`/`.opencode` dogfood mirrors.
- **Out of scope:** Network access, web search, and external documentation fetching; a new OpenCode routing agent; any Rust CLI change including `sce setup --bootstrap-context`; a `sce-context-sync` skill or any sibling-skill invocation; a phase package; changes to the existing five workflows' semantics.
- **Constraints:** The OpenCode routing role is the existing `shared-context-code` agent (`openCodeAgentSlug = "shared-context-code"` in the catalog record); no third routing role is introduced. `/brownfield` is phase-free and self-contained — the command is thin and invokes exactly one skill, and the skill owns argument parsing, investigation, the blocking clarification gate, contradiction disclosure, structure inference, writing, the quality audit, and every terminal layout. It never creates the `context/` root. Generated target layouts stay ephemeral and canonical behavior stays Pkl-owned, with the project-root mirrors kept byte-identical to canonical generation.
- **Non-goal:** Turn `/brownfield` into a recurring context-maintenance or drift-repair command. Ongoing maintenance stays owned by the task and plan synchronization phases; `/brownfield` is a cold-start and gap-fill tool.

## Assumptions

- The command slug is `brownfield` and the skill slug is `sce-brownfield`, following the catalog's `sce-{commandSlug}` convention. The draft's `sce-context-builder` name is not used.
- The argument surface is `[rebuild] [path ...]`: an optional leading literal `rebuild` token grants rewrite authority, and every remaining token is an additional local documentation path (file or directory, inside or outside the repository) to read as evidence. Anything else is invalid usage.
- Claude `allowed-tools` are `Read, Glob, Grep, Edit, Write, Question, Skill, Bash` — `Bash` for Git history, `Question` for the blocking clarification gate, `Edit` for additive `context-map.md` updates, and no `Task` because the workflow delegates to nothing.
- Adding one workflow adds nine generated artifacts (one command/prompt plus two skill documents per target), so the exact artifact contract moves from 61 to 70.
- "At least three months of Git history" is a floor measured from the current date, with older history read only when recent evidence points at a still-relevant architectural decision, migration, rename, deletion, or recurring risk.

## Open questions

- The confidence model is the draft's centerpiece, and its numbers are model-generated rather than calibrated against anything. A `72` and an `86` do not reliably mean different things, and the only score with real teeth is the `< 50` blocking threshold. The audit table risks reading as precision the workflow does not have. Alternative: keep the `< 50` gate and the `Verified` / `Strongly supported` / `Inferred` / `Clarification required` / `Contradiction resolved` statuses, and drop the numeric column from user-facing output. This does not block the plan — T01 authors the model as specified — but it is worth deciding before the workflow is used in anger.
- On a repository that already has curated context — this one has roughly seventy domain files — additive-by-default means `/brownfield` will mostly find that everything already exists and write little. That is the correct and safe behavior, and it means the workflow's real value is cold-start on a repository that has none. Worth confirming that matches your expectation before three tasks are spent on it, because the `rebuild` path is the one that would do meaningful work here, and `rebuild` is also the one that can destroy curated memory.
- `/brownfield` becomes the second writer of durable `context/` alongside the task and plan synchronization phases, which today own that authority exclusively. Two writers with independently authored structure rules will drift. The plan schedules an ADR and a `context-workflow-rules.md` update for this, but the shared rules stay duplicated in two Pkl modules rather than factored into one; factoring them is deliberately out of scope here.
