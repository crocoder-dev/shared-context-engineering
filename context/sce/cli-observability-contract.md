# CLI Observability Contract

## Scope

This document defines the implemented structured observability baseline for `sce` runtime execution.
It covers deterministic logger controls and terminal-routing behavior, default-backed log-directory routing with a one-time file fallback and bounded retention, the current logger and telemetry trait boundaries, config-backed runtime resolution, startup degradation behavior for invalid discovered config, and event emission boundaries in `cli/src/services/observability.rs`, `cli/src/services/config/mod.rs`, and `cli/src/app.rs`.

Runtime observability consumes the shared resolved observability config from `cli/src/services/config/mod.rs`: env values still win where supported, config-file values act as fallback, and defaults apply when higher-precedence layers are absent. The concrete logger stores the resolved `log_file_retention_limit` and uses it for creation-triggered primary and v2 cleanup. When default-discovered config files are invalid JSON, fail schema validation, or are not top-level JSON objects, observability resolution skips those files, collects the failure text in `validation_errors`, and continues with defaults; explicit `--config` / `SCE_CONFIG_FILE` selections remain fatal. Startup therefore keeps running with degraded observability defaults instead of turning discovered invalid config into a startup failure. Those resolved values are surfaced to operators through `sce config show`; `sce config validate` uses the same validation path but reports only validation status plus any errors or warnings.

## Runtime controls

- `SCE_LOG_LEVEL` selects log threshold with allowed values `error`, `warn`, `info`, `debug`.
- `SCE_LOG_FORMAT` selects log format with allowed values `text`, `json`.
- `SCE_LOG_DIR` configures the log-directory value used by the logger configuration surface and overrides config/default values.
- `log_to_file` is a flat config-file boolean that defaults to `true`; it explicitly controls whether records are written to the configured log directory and whether normal logger records are routed to `stderr`. When `true`, normal logger records are not routed to `stderr`; when `false`, only error-level logger records are routed to `stderr`. It resolves independently from `log_dir`.
- Defaults are deterministic: `log_level=error`, `log_format=text`, `log_to_file=true`, and `log_dir=<state_root>/sce/logs` when higher-precedence env/config inputs are unset. Omitting either file-logging property is valid.
- `log_file_retention_limit` is a flat config-file/default-only value with minimum `1` and default `10`; it has no environment variable or CLI flag, merges local over global, and appears in `sce config show` with provenance.
- The default `log_dir` is resolved by `cli/src/services/default_paths.rs` through `observability_log_dir()`; on Linux this is `$XDG_STATE_HOME/sce/logs`, or `~/.local/state/sce/logs` when `XDG_STATE_HOME` is unset.
- Invalid observability env values still fail invocation validation with actionable error text.
- Invalid default-discovered observability config files no longer block runtime config resolution by themselves; they are skipped and resolution falls back to defaults.
- After degraded observability config is constructed, startup emits one forced `warn`-level log per skipped discovered-file failure before command dispatch continues. With the default `log_to_file=true`, that logger record is written to the log file rather than `stderr`; the separate startup guidance remains a user-facing `stderr` diagnostic on successful command completion.
## Repository-local default in this repo

- This repository now ships a repo-local config at `.sce/config.json`.
- The local config sets `log_level=error` and `log_dir=context/tmp`.
- Running `sce` commands from this repository resolves `context/tmp` as the configured log directory unless `SCE_LOG_DIR` overrides it.

## Emission contract

- Command result payloads remain on `stdout`; user-facing diagnostics and text-mode sync progress remain on `stderr`.
- Emitted logger records are sent to tracing. When `log_to_file=true`, emitted logger records are written to the configured log file and are not emitted to `stderr`; when `log_to_file=false`, only error-level logger records are emitted to `stderr`, and no logger records are written to a file. This includes the forced invalid-discovered-config warning: it is not a terminal logger line under either file-routing mode.
- Each enabled or forced log operation appends the redacted rendered record to a file selected at emit time from the resolved `log_dir`, machine-local date, and optional caller-provided session ID, except when file logging is disabled.
- Sessionless file logs route to `<log_dir>/sce-<dd_mm_yyyy>.log`; session-aware file logs route to `<log_dir>/sce-<dd_mm_yyyy>-<sanitized_session_id>.log`.
- Session filename sanitization preserves ASCII letters, digits, `-`, and `_`; percent-encodes every other UTF-8 byte as uppercase `%HH`; and represents an explicitly empty `Some("")` session ID with the reserved `%EMPTY` token.
- `sce hooks diff-trace` and `conversation-trace` pass producer-native session context into this existing routing argument when available. Diff-trace logging never uses the AgentTraceDb-only `oc_`/`cc_`/`pi_` prefix; skipped conversation items use their own session; batch-wide conversation insert failures use the first valid insert's session. Agent Trace DB open failures use hook-specific error events (`sce.hooks.diff_trace.agent_trace_db_open_failed` and `sce.hooks.conversation_trace.agent_trace_db_open_failed`) and do not also emit their broader write/intake events for the same failure. Session IDs remain absent from rendered record fields unless separately supplied as fields.
- File routing creates the configured directory when needed, uses owner-only create permissions on Unix, and serializes writes through a fixed set of in-process lock stripes (see the next bullet).
- Log-file write synchronization is a static array of 64 `std::sync::Mutex<()>` stripes in `cli/src/services/observability.rs`; a path selects its stripe via a deterministic `DefaultHasher::new()` hash modulo the stripe count. Synchronization memory is constant and independent of the number of distinct log paths (no per-path allocation or eviction). Writes to the same path are serialized within one process across threads and independent `Logger` instances; distinct paths that hash to the same stripe only contend, they never fail. No cross-process coordination exists or is guaranteed. A call holds at most one stripe at a time: the primary path's guard covers persistence and retention cleanup and is released on success and failure before the v2 fallback acquires its own stripe, so primary and v2 paths sharing a stripe cannot deadlock. A poisoned stripe (a panic under the guard, realistically only inside the retention cleanup callback) fails every path on that stripe with the unchanged `failed to lock log file '<path>': ...` error, does not trigger the fallback, and is never recovered.
- If file logging is enabled and the selected primary file cannot be opened, appended to, or flushed, the logger retries the complete rendered record exactly once at a sibling path with `-v2` inserted before `.log`: `sce-<dd_mm_yyyy>-v2.log` or `sce-<dd_mm_yyyy>-<sanitized_session_id>-v2.log`. Existing v2 files use the same create-or-append and striped serialization behavior.
- Successful v2 persistence suppresses the terminal `Failed to write SCE log file` diagnostic and leaves the CLI command result unchanged. If both persistence attempts fail, the logger emits one redacted terminal file-write diagnostic to stderr and continues fail-open; a partial primary append may therefore coexist with the complete fallback record.
- Directory creation, primary lock acquisition, and retention cleanup failures do not trigger alternate-name generation. The fallback attempt is non-recursive: no v3, timestamped, random, or unbounded variants are tried.
- After a successful write to a newly created primary or v2 SCE log file, the logger runs one best-effort retention pass over direct regular `*.log` children of `log_dir`. Existing-file appends do not scan or delete files. Cleanup keeps the resolved `log_file_retention_limit` newest files (default `10`). Files are ordered newest-first by filesystem modification time with path/name ordering as the deterministic tie-break, and older `.log` files are removed regardless of whether their names are SCE-owned.
- Retention is non-recursive and ignores non-regular entries plus non-`.log` files such as directories, symlinks, database files, and extensionless artifacts. Directory scan, metadata, or deletion failures do not fail the completed write; cleanup emits a redacted direct-stderr diagnostic without re-entering `Logger::log` and leaves entries it cannot safely process intact.
- Each emitted record includes a stable `event_id`.
- Current app-level event identifiers:
  - `sce.app.start`
  - `sce.config.invalid_config` (warn level - emitted once per skipped invalid discovered config file during startup)
  - `sce.config.file_discovered` (debug level - logged for each discovered config file)
  - `sce.command.raw_args` (debug level - logged at command parsing entry)
  - `sce.command.parsed`
  - `sce.command.dispatch_start` (debug level - logged before dispatch)
  - `sce.command.dispatch_end` (debug level - logged after successful dispatch)
  - `sce.command.completed`
- Error logging uses the pattern `sce.error.{code}` where `{code}` is the classified error code (e.g., `sce.error.SCE-ERR-RUNTIME`) for the local file/stderr record only; the tracing event for the same record carries the typed `sce.error.{parse,validation,runtime,dependency}` identifier instead (see Tracing boundaries).
- All `CliError` instances are logged via `Logger::log_cli_error()` before user-facing stderr diagnostics are written; observability retains full technical detail independently of what is rendered to the terminal, and never writes a second competing stderr diagnostic for the same error.
- Event records include deterministic metadata keys used by automation (`command`, `failure_class`, `component` when applicable).
- Error log records include `error_code` and `error_class` fields for structured observability, plus `error_surface` (`user` for `CliError::User`, `internal` for `CliError::Internal`), `user_error` (the catalog `UserError::key()`, present only for `CliError::User`), and `error_source` (the full technical source chain, present whenever one was preserved — always for `CliError::Internal`, and for `CliError::User` only when constructed with `CliError::user_with_source`).
- App runtime wraps parse/dispatch in `Telemetry::with_default_subscriber`. Production uses `RuntimeTelemetry`: `NoopTelemetry` (no tracing subscriber, no tracer provider) unless the opt-in standalone OTel runtime is selected (see Standalone OTel runtime). Raw `tracing` events emitted outside `Logger`, such as `sce.resilience.retry` and `sce.agent_trace_db.contention_exhausted`, have no production sink unless a subscriber is attached that way. `Logger` records still follow the file/stderr routing below.

## Tracing boundaries

Any `tracing` subscriber attached to the process can read what `sce` emits, so tracing content is allowlisted by construction rather than redacted. `cli/src/services/observability/tracing_boundary.rs` owns Boundary A and `cli/src/services/observability/otel_policy.rs` owns Boundary B.

- Boundary A (existing `sce`-target events): all `sce`-target event emission lives in three typed functions in `tracing_boundary.rs`: `emit_logger_event(LogLevel, EventId)`, `emit_retry_event(OperationClass, u32, u32, u64, u64)`, and `emit_contention_event(DbName, OperationClass, u32, u64, u64, u64)`. They accept only closed enums, the registry-backed `EventId` newtype (private field, built only by `EventId::classify`, `EventId::from_cli_error`, or its associated constants), and numerics, and use static messages. `Logger`, `resilience.rs`, and `db/mod.rs` call these and contain no `tracing` macro. The retry event now carries target `sce` (previously the incidental module path). Each enabled logger record emits one event with only `event_id` and `log_level`. `event_message`, serialized `fields`, `error_source`, `error`, `last_error`, paths, and hook payloads never reach `tracing`; local file/stderr rendering and its raw event identifiers are unchanged.
- `event_id` reaches tracing only if it is a member of the closed, sorted `TRACING_EVENT_IDS` registry (shape `[a-z0-9_.]{1,64}`, uniqueness and ordering unit-tested); any unknown, dynamically built, or test-only identifier becomes `sce.unclassified`. `log_cli_error` derives `sce.error.{parse,validation,runtime,dependency}` from the typed `FailureClass`, never from the formatted string. New static identifiers must be added to the registry.
- `sce.resilience.retry` and `sce.agent_trace_db.contention_exhausted` record only `event_id`, enumerated `operation` (`OperationClass`) and `db_name` (`DbName`) with an `unclassified` fallback, numeric counters/durations, and the constant `cause`.
- A syn-based test-only audit (`tracing_boundary/audit.rs`, `syn` and `proc-macro2` dev-dependencies) parses every `cli/src` file as Rust, so comments and string literals are never mistaken for code. Outside `tracing_boundary.rs` it rejects any `tracing`-rooted path, import (including aliases, globs, and `extern crate`), `#[tracing::...]` attribute, macro named `error`/`warn`/`info`/`debug`/`trace`/`event`, and macro token stream mentioning `tracing::`. Inside the boundary (non-test code) it requires `tracing::`-qualified `error`/`warn`/`info`/`debug`/`enabled` only, `target: SCE_TRACING_TARGET`, a single brace-free string-literal message, allowlisted field names, and values that are same-named bindings of numeric parameters or `as_str()` results of closed-type parameters (or approved constants). No per-file counts are maintained. Span macros and `#[tracing::instrument]` are also rejected outside the boundary, so T03 span creation must go through a typed boundary function.
- Boundary B (OTel export surface, enforced by the standalone runtime's exporter): the `sce::otel` target, enumerated span names (`OtelName`), and the closed `OtelAttribute` enum (`CommandName`, `Outcome`, `ErrorCategory`, `OperationType` = `OperationClass`, plus numeric `DurationMs`/`Count`/`Attempts`). Every string value is a static `as_str()` of a closed enum, so there is no string-carrying attribute type. `OtelAttribute::admit` and `admit_otel_record` map raw `(key, value)` input back only by exact lookup against those enums and drop other targets, unknown names/keys, unknown or mismatched values, and anything resembling exception messages or stack traces. Character-class validation is no longer used.
- Capture tests (`tracing_boundary_a*`) use a dependency-free capturing `tracing::Subscriber` rather than the OTel exporter; `tracing_boundary_b*` additionally drive the real exporter layer with an in-memory exporter.

## Standalone OTel runtime

`cli/src/services/observability/otel_runtime.rs` is the opt-in, statically dispatched OTel runtime. It is a private subscriber, never a global one, and exports only the Boundary B surface.

- Enablement: only the environment switch `SCE_TELEMETRY=standalone` (exact value). Resolution (`resolve_telemetry_mode`) reads that single key from an injected environment source; repository `.sce/config.json` cannot enable it and no `otel` config key exists. No managed token is ever attached. `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (used as-is) or `OTEL_EXPORTER_OTLP_ENDPOINT` (`/v1/traces` appended) selects the receiver; otherwise the SDK default applies.
- Hook-export gate: when standalone is requested, the parsed command is classified through the typed `RuntimeCommand::is_hook_invocation` (exhaustive match; `hooks` and `policy` variants are hook invocations). Hook invocations, and arguments that fail to parse, resolve to `NoopTelemetry` before any exporter is built, regardless of inherited `SCE_TELEMETRY`/`OTEL_*`. Initialization failure also falls back to `NoopTelemetry`; telemetry failure never changes stdout, exit codes, or hook decisions. The gate stays in force after the T05 benchmark; its candidate 100 ms hook flush budget and the conditions for any future user-owned enablement are recorded in [hook telemetry benchmark](hook-telemetry-benchmark.md).
- Scoping: `OtelTelemetry` builds a `Registry` plus `tracing-opentelemetry` layer filtered to spans on target `sce::otel` with enumerated `OtelName`s, and `ScopedDispatch::scope` (in `tracing_boundary.rs`) attaches it to the command future with `WithSubscriber::with_subscriber`, so it is active on every poll across Tokio worker migration. Spawned tasks do not inherit it: production `tokio::spawn` that must be traced goes through `spawn_in_current_scope` (`.with_current_subscriber()` + `.in_current_span()`); today only the credential-refresh spawn in `agent_trace_sync/control_plane.rs` does. `spawn_blocking`/`std::thread` sites are untraced until the operation-span tasks wrap them.
- Export: OTLP/HTTP protobuf through the SDK `BatchSpanProcessor` (its own `OpenTelemetry.Traces.BatchProcessor` thread, bounded drop-on-full queue). The HTTP client has 750 ms connect/total timeouts and redirects disabled, and is built on a separate init thread (the blocking `reqwest` client must not be built or dropped on a Tokio runtime); if the platform certificate store cannot be loaded it falls back to an empty-root client so plaintext local receivers still work.
- Boundary B enforcement is split by what each layer can actually observe:
  - Subscriber layer (`scoped_dispatch` `filter_fn`, the only place the originating `tracing` target is visible): accepts spans only when the target is exactly `sce::otel` and the name is an enumerated `OtelName`; ordinary `sce` logger events are never spans and are rejected, and a span named like an allowed `OtelName` is still rejected when emitted from target `sce` or any other module target.
  - Exporter wrapper (`BoundaryBExporter`, wraps the OTLP exporter): `SpanData` carries no originating `tracing` target, so the wrapper never claims target filtering and no target attribute is fabricated. It independently drops spans whose name is not an `OtelName`, re-admits every attribute through `OtelAttribute::admit` (a canonical decimal string is accepted only for numeric keys, because `tracing-opentelemetry` records `u64` fields as strings), drops unclassified attributes, clears events and links, and blanks error status descriptions. Tests: `tracing_boundary_b_production_subscriber_rejects_wrong_target` (subscriber) and `tracing_boundary_b_exporter_wrapper_enforces_policy_without_layer_filter` / `tracing_boundary_b_exporter_wrapper_cannot_observe_the_tracing_target` (wrapper, explicitly limited to name, attribute, event, link, and status guarantees).

## `sce.command` span and bounded shutdown

- `CommandSpan` (in `tracing_boundary.rs`, the only production `tracing::span!` site, accepted by the audit only with `target: OTEL_TARGET`, `Level::INFO`, an enumerated name, and allowlisted fields recorded as `Empty`) is created in `run_command_lifecycle_with_context` after the arguments parse successfully, wraps `execute_command_phase`, and records only `sce.command.name` (`CommandName`), `sce.outcome` (`success`/`failure`) and, on failure, `sce.error.category` (from `FailureClass`) plus an error status with an empty description. Parse failures and hook invocations in ordinary standalone mode produce no span. No message, argument, path, or stack trace is recorded. The span closes when the command future completes, before any flush.
- Trace-context propagation: `trace_context::extract_remote_parent` (pure over an injected environment source; `app.rs` passes the process environment) feeds `TRACEPARENT`/`TRACESTATE` to the SDK `TraceContextPropagator` and yields a context only when the resulting span context is valid and remote. `CommandSpan::start(command, remote_parent)` applies it with `OpenTelemetrySpanExt::set_parent`, so a valid header gives a child with the exact trace ID, parent span ID, sampled flag, and trace state. Malformed or absent headers give an independent root and no parent is invented. An unsampled parent is honored by the provider's parent-based sampler, so nothing is exported. `tracestate` rides on the span context only and is never recorded as an attribute. Extraction runs only inside the OTel dispatch, so disabled and hook-gated invocations ignore both variables. Which harness subprocesses actually receive `TRACEPARENT` is not claimed here; it is measured separately.
- `OtelTelemetry` holds its tracer provider and scoped dispatch in a single `Teardown`. `run_with_dependency_check_and_streams` renders stdout/stderr first, flushes them, then calls `RuntimeTelemetry::shutdown(self)`, which consumes the telemetry: the `Teardown` moves to a dedicated `sce-otel-shutdown` OS thread that calls `SdkTracerProvider::shutdown_with_timeout(budget)` exactly once (the SDK batch worker exports the remaining queue, then shuts the exporter down) and drops the provider and dispatch there; the caller awaits a oneshot with `tokio::time::timeout(budget)` and never joins. No lock is held at that point and no Tokio worker blocks. After an explicit shutdown the SDK `is_shutdown` flag makes any later final drop of a retained provider/dispatch clone non-blocking. If an `OtelTelemetry` is dropped without `shutdown`, `Drop` hands the same teardown to a detached thread instead of blocking the caller. `ShutdownOutcome` is `Completed`, `Incomplete` (deadline or SDK error), or `Unavailable` (shutdown thread creation or handoff failure). On that failure path the `Teardown` is leaked with `std::mem::forget` so neither `shutdown_with_timeout` nor the final provider drop (which runs SDK shutdown) executes on the caller; memory is not reclaimed before process exit, which is accepted for this short-lived CLI. Worker creation is injected through a generic closure for tests (`shutdown_with`, `release_with`).
- Bounded-shutdown subprocess tests treat any hard timeout as a failure and enforce bounds against the maximum sample (no retry, no outlier allowance).
- Budget: `SCE_TELEMETRY_FLUSH_TIMEOUT_MS`, default 1000 ms, accepted range 1 to 5000 ms (anything else uses the default). The OTLP client uses one attempt (`RetryPolicy::disabled()`; the SDK default of 3 retries added about 450 ms when the connection was refused) with 750 ms connect/total timeouts. `BatchSettings::PRODUCTION` fixes the batch processor explicitly (queue 256, batch 64, delay 2 s, drop on full) and overrides every `OTEL_BSP_*` variable the SDK would otherwise read.
- Telemetry failure never changes stdout, stderr, exit code, hook decisions, or durable state (`telemetry_offline_parity_*`, real `sce` subprocesses against reachable, refused, accept-but-never-respond, and non-routable receivers).

## Controlled test receiver (`telemetry-test-receiver`)

- Cargo feature `telemetry-test-receiver` (off by default; not used by `.#default`, release, crates.io, or Flatpak). Without it the code, the environment variable names, and the lifecycle markers do not exist (`telemetry_test_receiver_inert_without_the_feature` plus the `packaged-binary-excludes-test-receiver` flake check, which greps the `.#default` binary for the variable names and proves a loopback listener receives nothing).
- With the feature, `SCE_TELEMETRY=test-receiver` plus `SCE_TELEMETRY_TEST_RECEIVER_ENDPOINT=http://<loopback IP literal>:<port>` exports to that endpoint only. Resolution (`test_receiver::resolve`) is pure over an injected environment, has no credential field, never touches the auth DB, ignores `OTEL_*` endpoint/timeout/protocol, and wins over standalone. The SDK exporter merges `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_TRACES_HEADERS` unconditionally, and that cannot be disabled without a new dependency, so resolution fails closed (telemetry stays disabled) when either header variable is non-empty. Hostnames, HTTPS, non-loopback, paths, userinfo, and port 0 are rejected. Hook-style invocations export only to this receiver (the single exception to the hook-export gate).
- `SCE_TELEMETRY_TEST_LIFECYCLE_FILE` makes the process append `command_complete`, `shutdown_begin`, `shutdown_end`, and `process_exit_requested` lines (monotonic nanoseconds since the first marker) to that file only, in any telemetry mode, for shutdown measurement.
- `scripts/check-cargo-test-count.sh <minimum> <command...>` fails when the command fails or the summed `N passed` is below the minimum, so a filter matching zero tests is never a pass; `scripts/test-check-cargo-test-count.sh` tests it. Flake checks `cli-telemetry-default-features` and `cli-telemetry-test-receiver` run the default-feature and feature-enabled passes separately through it with recorded minimums; `cli-clippy` already uses `--all-features`.

## Format contract

- `text` format emits single-line key/value records with fixed key ordering: `timestamp`, `log_format`, `level`, `event_id`, `message`, then optional fields.
- `json` format emits a single-line object with fixed top-level keys: `timestamp`, `log_format`, `level`, `event_id`, `message`, `fields`.
- Timestamps are UTC ISO8601 with millisecond precision (e.g., `2026-03-20T14:30:00.123Z`) generated via `chrono::Utc::now()`.
- Logger threshold behavior is deterministic and severity-based (`error < warn < info < debug`).
- Startup invalid-config diagnostics use an explicit warn-emission path so the warning is still recorded even when degraded defaults resolve to `log_level=error`; normal logger stderr routing still follows `log_to_file` and severity.
- Rendered records remain deterministic line-based strings. Logger records are routed according to `log_to_file`; log-directory files contain the same redacted rendered lines, do not add session IDs to the record schema automatically, and are bounded by creation-triggered `*.log` retention.

## Observability trait boundaries

- `cli/src/services/observability/traits.rs` exposes the `services::observability::traits::Logger` trait with the current logging API: `info`, `debug`, `warn`, `error`, and `log_cli_error`, each accepting `Option<&str>` session context used only for file routing.
- The concrete `services::observability::Logger` implements the trait while retaining the existing inherent methods and behavior.
- `NoopLogger` is available from the same traits module for tests and future dependency-injected services that need a logger without side effects.
- The same traits module exposes deliberately non-object-safe `services::observability::traits::Telemetry`: async `with_default_subscriber<F, Fut>` accepts generic `FnMut() -> Fut` actions and awaits command-lifecycle execution through static associated capability dispatch.
- `NoopTelemetry` (same traits module) awaits the action once and installs no tracing subscriber or tracer provider; production selects it unless the standalone runtime is enabled. Statically dispatched telemetry attaches its subscriber to the command future with `WithSubscriber::with_subscriber`; holding a thread-local `with_default`/`set_default` guard across awaits does not scope every poll on multi-thread Tokio.
- `cli/src/app.rs` stores the concrete production `Logger` and the two-variant `RuntimeTelemetry` enum (`Noop` or `Otel`, chosen after runtime init by `select_runtime_telemetry`) as `AppRuntime` fields, creates borrowed `AppContext` views for command execution, and exposes logger/telemetry access through associated-type context accessors instead of owned `Arc<dyn ...>` fields or object-erased accessor return values.
- Final stream rendering uses `RunOutcome<L: Logger>` in `cli/src/services/app_support.rs`, so classified-error and stdout-write-failure logging depends on the logger trait boundary rather than the concrete production logger type.
- `run_command_lifecycle` expects the telemetry subscriber action to execute command dispatch at most once; arguments and the mutable stderr reference are taken from single-use options before constructing the action future; if a telemetry implementation invokes the action again, the app returns a `SCE-ERR-RUNTIME` classified error rather than panicking or reparsing consumed arguments.

## Log directory config safety contract

- `log_to_file` is resolved from the config file or its backward-compatible `true` default and is surfaced with provenance by `sce config show`.
- `log_to_file` and `log_dir` are independent configuration properties. Omitting `log_dir` uses the default location, and omitting `log_to_file` defaults to enabled file logging; neither omission creates a cross-property validation error.
- `log_dir` config-file values are schema-validated as non-empty strings; an explicitly empty config value fails schema validation before runtime startup. Setting `log_to_file` to `false` disables file logging without changing `log_dir` resolution.
- `SCE_LOG_DIR` env values are resolved with env-over-config-over-default precedence and rejected when explicitly empty.
- Logger construction validates resolved `log_dir` as non-empty without opening files; directory creation, per-operation local-date file selection, append writes, Unix owner-only create permissions, and creation-triggered retention happen at log emission time.

## Ownership and verification

- `cli/src/services/config/resolver.rs` owns shared observability value resolution, including independent config-file/default `log_to_file` and `log_dir` resolution, config-file discovery/merge, env-over-config/default precedence for supported runtime inputs, default `log_dir` resolution through `default_paths::observability_log_dir()`, and config-file/default-only `log_file_retention_limit` resolution.
- `cli/src/services/observability.rs` owns runtime logger construction from resolved values, storage and application of `log_file_retention_limit`, `log_dir` non-empty validation, level filtering, tracing-event enablement checks, record rendering, local-date/session file-name selection, session filename sanitization, primary append plus one-time v2 fallback persistence, and best-effort `.log` retention; `cli/src/services/observability/traits.rs` owns the logger and telemetry trait boundaries plus the no-op logger implementation; `tracing_boundary.rs` and `otel_policy.rs` own the tracing allowlists described above.
- `cli/src/app.rs` owns lifecycle event emission around parse/dispatch success and failure paths, resolves observability config before command dispatch, emits startup invalid-config warning events for skipped discovered config files, wraps dispatch inside the observability subscriber context, and guards the single-use command-dispatch action against repeated telemetry invocation with a runtime-classified error. `cli/src/services/app_support.rs` owns final stdout/stderr rendering and generic logger-backed classified-error logging.
- Retention-specific validation uses packaged CLI smoke checks for config/schema behavior and direct review of the primary/v2 logger cleanup plumbing. The root flake check suite validates the build, lint, formatting, generated parity, and remaining repository tests; no retention-specific Rust test module is currently kept in `observability.rs`, `config/resolver.rs`, or `config/schema.rs`.
